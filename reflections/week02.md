1. **Aegis Flight-Control Software Update**

The software process model I would use for this update would be the **waterfall model**.



The reasons I would use the waterfall model:

* The requirements are **well understood and stable** which is key principles of the waterfall model. It is sequential and plan driven. "Requirements are unusually well understood and stable — the failure mode and required warning behaviour are precisely specified by engineering analysis before any coding begins". 
* This update also requires **extensive documentation** at every stage, which is another key principle of the waterfall model. " The client organisation has a large, well-resourced quality assurance department and expects extensive documentation at every stage".
* There is **no timeline pressure**, giving them 12-18 months to develop the system. This ensures that everything can be done sequentially and to plan. "certification timelines (often 12-18 months) dominate the schedule".
* There is **no user involvement** for this software update, a key feature of the waterfall model.
* There is **high risk** with this project which are specified by the engineering analysis before any coding begins. "the failure mode and required warning behaviour are precisely specified by engineering analysis before 
* any coding begins". 
* A **risk** of the waterfall model is that the requirements are **required upfront**, making requirment changes a little trickier. Another risk would be **testing is** **late** and close to when software is delivered. Finally, the **changes can** be quite **costly**. "A defect in this software could endanger lives, so the cost of a field-discovered defect is extremely high".



2\. **Riverside Bakery Marketing Website**

The software model I would choose for this website is the **prototyping/iterative** model. 



The reasons I would use the iterative model:

* The **requirements are unclear and minimal** at best. The iterative model builds **small portions of all features** repeatedly, allowing room for the owner's opinion, which is always changing. The incremental would be a close second, but due to the deadline of three weeks, building in small increments would not be viable, iterative would prioritise getting the entire system complete and updating it accordingly (to the owner's wishes). "The owner has never commissioned a website before and openly admits she is 'not sure exactly what it should look like' until she sees some options". 
* For this website there is **no safety or regulation dimension** for this project, meaning the safety/risk is quite low. 
* The iterative process is key as there is **early detection and continious** improvement for the website based on the owner's preference. There is heavy customer invovlement with the owner specifically as she gives feedback daily to change specific parts of the website. "The owner is available to give feedback almost daily but tends to change her mind about visual details (colours, wording) once she sees a working draft".
* As mentioned above, **there is timeline pressure** as the owner would like this website up and running in three weeks.
* **Documentation is quite low**, the priority is designing the website and getting it out there to customers/end users; a key principle of the iterative model.
* A **risk** of the iterative model is that **arichictecutal/ design problems may appear later** with such a tight deadline. Another risk is, if using the protyping iterative development, **developers may feel presured to release a system but is really just the prototype**.



3\. **CampusCircle Community App**

The software model I would choose for this app is the **agile model** which combines both the **iterative** and **incremental** process models.



The reasons I would use the agile model:

* The **requirements aren't stable** as they are constantly changing. Even after the project is delivered, the requirements will still be changing as they want to use customer feedback to improve the website. Changing requirments is a key feature for the agile method. "The founders have a rough idea of core features (browse clubs, RSVP to events, in-app chat) but expect these to change significantly once real students start using early versions — they specifically want to release something usable within a month and adapt based on user behaviour and feedback, rather than fully specifying the app upfront".  
* **Customer feedback is frequent** and the driving force for developing this application, another key feature of the agile method. This is to ensure the application is the best it can be and what the user's actually want. 
* They want to **have a working system** in a month (this is where the iterative side of agile comes in) but this application will be changing incrementally with each new user request for the application. 
* There is **less documentation** than the waterfall model for example as they focus on having a working system more. 
* The **risk is relatively low** besides the safety/data protection. 
* The team is small and co-located, this is good as they will need to regularly come together and discuss the next steps of developing the app. 
* A **risk** would be that, due to changing requirements, it would be hard to size increments with each user incremental change.

1. **MoveIt Health Fitness App**

MoveIt is a health and fitness tracking application developed using .NET MAUI and C#. The application allows the user to record personal information, track exercise and monitor fitness progress. The website will need to be somewhat operational in the next month with basic features and a simple UI design. The budget is low and the owner is not quite sure what they wants the system to do or look like. The owner would like to take customer feedback once the website is up and running to improve it.



I would choose the **agile method** because:

* The **requirements are incredibly unclear**, UI and functionality wise.
* The **owner wants customer feedback** AFTER the application is up and running. This would require both iterative model (to get something functional out in a month) and incremental (to respond to customer feedback and incrementally change the website), making agile the most suitable option for a process model.
* The **risk is relatively low** for this project. 
* There is **less documentation** for this project as the main goal is to get something functional out in a month and to build on the website based on customer feedback.
