**## The Four Process Activities: RetailSync Case Study** 

**Specification:** Definition of requirements for the RetailSync was incredibly **weak**. There was no written documentation or proper establishment of what needed to be accomplished. **"The IT director held a single one-hour meeting with the lead developer to describe 'roughly what was needed'. No written requirements document was produced."**



**Development:** While development itself in terms of developers designing and building were present, the process it self was overall **weak**. There was no coding standards or code reviews. These are essential when working as a team to create software. There was no care or attention towards where the data was going or how it was processed leading to overridden work. There was also no consulting to regularly keep track of what was going on with the project. **"There were no shared coding standards and no code review process — each developer pushed code directly to a shared folder on a network drive, occasionally overwriting a** 

**colleague's changes without noticing."**



**Validation:** The validation in terms of checking and testing their software against requirements was horrifyingly **weak**. They did not allow enough time to properly test and validate their coding in general, and further did not test against the requirements at all. **"No warehouse staff tested the system before go live. No test cases had been written down anywhere during development."**



**Evolution**: Modification of requirements as they changed were also present but incredibly **weak**. The definition of the specifications/requirements were already unwritten and was in the mind of a developer. Due to the specification stage being weak/non existent, this led to the evolution being weak too.  **"This had not been part of the original (unwritten) brief. The lead developer estimated this would 'probably add a few weeks' and did not revisit the existing design, instead patching the second warehouse's requirements on top of the existing schema."**



**4.**

I believe that the single failure that did the most damage overall was the failure to establish and define the requirements at the beginning. Requirements are essential for every stage of the software process. For the development phase it is essential for developers to know the requirements so they know exactly what they are building and designing. In the validation phase it is these same requirements that the software at every stage is being tested against. Even in the evolution phase, any modification of requirements would require revisiting the previous requirements that were already established, whether that be to add to them, modify, remove etc. An essential list of requirements is incredibly important to do in the beginning of the software process which is what I believe led to the demise and failure of the project. A good software process does not guarantee a good product, but it certainly increases the likelihood of a successful one.
